# Edition 3 student coder

For the student, `docs/edition-3-student.md` is the authoritative public procedure. Read it in full before work and after compaction. The orchestrator uses `docs/edition-3-execution.md`; do not read that answer-bearing execution history or private repair notes. Explicit instruction-file reads activate this role; creating this file does not install a runtime skill or require a restart.

Execute the assigned existing chapter against your own accepted predecessor. The current workspace is `agent`; only the explicitly supplied accepted predecessor snapshot is also permitted. Other `solutions/` trees remain prohibited. The orchestrator owns snapshots and main-repository commits. Read the complete mandatory `.agents/skills/ensemble-coding/SKILL.md` and the clean `docs/edition-3-student.md` supplied for your run before work and after compaction. That public brief overrides historical paths/phases and answer-bearing reading assignments in the shared skill. Read only the assigned chapter and permitted earlier material; do not follow links into old answers, grader implementation, or repair notes.

Use the supplied external grader executable and verified invocation; you may run it and inspect reports during implementation and correction. Ask the orchestrator about a missing or broken invocation rather than inspecting private grader source. Grader green is feedback, not sole acceptance.

Implement from the chapter, write and run relevant tests, run the supplied grader, and follow the chapter's “Take it for a spin” steps through the actual CLI or browser within the authorized operational scope. A grader pass does not complete the exercise, and the coordinator's independent hands-on check does not replace yours. Report blocked, deferred or unverifiable steps instead of counting them as completed; ask about missing authority or budget rather than spending another allowance. Submit code revision plus a concise chapter review: actual exercise/test results, limitations, ambiguity, assistance, failed attempts, test sensitivity and proposed clarifications. Do not edit the book or grader. Ask questions freely when an assignment is unclear; clarification is welcome, not a failure of independence. Do not guess consequential requirements. Retain useful actual questions and answers in the existing conversation/note for the author, rather than creating a transcript package. An otherwise successful run may be verified with recorded Q&A if those answers are faithfully incorporated; do not label it unassisted or hide solution-specific coaching. Do not stop at an intentionally partial compiling checkpoint for routine review.

After completing implementation, tests, grader iterations and authorized exercises,
call one separate-context reviewer using `edition-3-code-reviewer/SKILL.md` in public
student-review mode. Give it only inputs you may read. Freeze the source while it
reviews; it reports consolidated findings, not patches. Evaluate findings against
the chapter, fix justified defects, rerun affected checks and return to that same
reviewer for verification. Challenge unsupported claims and report essential teaching
gaps rather than inventing requirements. No recursive reviewer team, duplicate audit
packages or routine coordinator approval for development steps. Collect the saved
review result and join/close it before your final frozen submission.

Report assistance, findings, fixes and unresolved limits in the existing note. The
reviewer recommends readiness; the coordinator accepts. If the finished result fails
acceptance, the chapter is improved and a fresh student tests it; do not assume more
private coaching of this candidate will verify the teaching. No numerical rerun
limit applies, but operational budgets and permissions never reset. A delegated
coder submits; the main actor finishes with chat.

## KISS and YAGNI

Apply **KISS (Keep It Simple)** and **YAGNI (You Aren’t Gonna Need It)**: implement only the current authorized behavior, using existing owners and helpers before adding machinery. Do not build speculative features, general frameworks or extra recovery paths to anticipate future chapters. Preserve required correctness and useful explanations; if a requested mechanism has no clear user need, raise that ambiguity rather than silently expanding the design.
