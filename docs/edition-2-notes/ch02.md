### Commands and environment

- No arguments: Chapter 1's JSON-lines stdin/stdout interface. Human `chat`
  remains a separate mode using the same Agent.
- `render LOG`: read the named JSON-lines log and print one vendor request JSON
  to stdout, with no network request. Target configuration comes from the environment.
- `dump`: **load the file named by `CH02_LOG` and emit its log as JSON-lines to
  stdout**. The grader invokes this in a fresh process after the chat process
  exits. It also supplies prewritten logs through `CH02_LOG`. This is a load and
  serialization operation, not a model request or a stdin directive. Invalid
  log data is refused with a nonzero exit and a diagnostic, as the chapter requires.
- During a session, persist its events to `CH02_LOG` so the separate `dump`
  process can read them. The grader sets this path; the chapter does not specify
  a default filename when it is absent. Choose a small usable default and record it.
- The three-vendor harness supplies `LLM_VENDOR` (`anthropic`, `openai`,
  `gemini`), `LLM_MODEL`, `LLM_API_KEY`, and `LLM_BASE_URL`. It also supplies the
  same base URL under `ANTHROPIC_BASE_URL`, `OPENAI_BASE_URL`, `GEMINI_BASE_URL`.
  Preserve Chapter 1's `ANTHROPIC_*` configuration when generic settings are absent.
- `LLM_RESOLVED_MODEL`, when nonempty, is an explicitly known exact model
  identity; `LLM_MODEL` is the requested routing name. The fake may return a
  different identity from that routing name. This environment field is omitted
  from the chapter's exercise contract; distinguish the requested name from the
  known identity when applying its provenance rule. Empty means no explicit
  identity was supplied. Do not add a discovery service or hardcode fake model IDs.

### Stdio messages

Each input/output message occupies one JSON line. Ordinary input is
`{"user":"Hello"}`; its answer is `{"assistant":"..."}`. On EOF, report cumulative
usage as `{"usage":{"input":0,"cache_write":0,"cache_read":0,"output":0}}`,
with actual counters in place of the illustrative zeros. Stdout carries protocol
only; diagnostics belong on stderr.

The missing directive is **`{"ephemeral":"STATUS=ready"}`**, with a string
payload. Acknowledge it as **`{"ack":"ephemeral"}`**. It queues that content for
the next request; receipt alone does not request a model response. The chapter
already specifies its event/reducer semantics: record a system message, deliver
once on the next request, and never retain it as ordinary dialogue. The README's
`ephemera` object and `{"ok":true}` acknowledgment are obsolete for this harness.

The Chapter 2 harness does **not** send stdin directives to inject tool results,
redact entries or dump a path. It supplies tool/redaction events inside input
logs for `render`. Do not build an extra command protocol to fill an apparent
hole. Hints, interrupts, asynchronous mailboxes and actual tool execution remain
outside this chapter, as its prose says.

### Supplied log input shapes

Tool results are log events, not injected stdio commands. For example, after
the corresponding call in a log:

```json
{"seq":4,"type":"tool_returned","time":"2026-01-01T00:00:03Z","tool":{"call_id":"example-call","parts":[{"type":"text","text":"example result"}]}}
{"seq":5,"type":"redacted","time":"2026-01-01T00:00:04Z","redact":{"from":4,"to":4,"level":"redact_result","reason":"compaction"}}
```

These are illustrative rows, not a complete conversation. A human message nests
its actor/parts under `message`; a response nests parts/usage/provenance under
`response`; a tool event uses `tool`. The chapter's enums and part shapes remain
the source of semantics. The header is `{"log_version":1}` and does not take a
sequence number. Ref kinds on supplied input are numeric: 1 path, 2 URI, 3 handle;
0 is invalid, matching the chapter's `iota+1` definition. No hardcoded exhibit
strings, expected answers, solution code or rendering algorithms were supplied.
