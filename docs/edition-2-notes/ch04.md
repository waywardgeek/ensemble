Exact clarification supplied:

- `ai_callback_delay` is a JSON number of **seconds**, including fractional
  values such as `0.2`; it is not a duration string. `ai_callback_pattern` is a
  regex string and `max_output_bytes` an integer byte cap, as the prose describes.
- `wait_for_job`, `send_input` and `kill_job` identify the target using integer
  `handle`. `send_input` carries string `input`. For example:
  `{"handle":1,"input":"p answer","ai_callback_delay":10}`.
- The fixture sends commands without a trailing newline to both a line-reading
  echo program and `dlv`. Thus the required default submits a **line** to the
  PTY, including its line terminator. This newline requirement is inferred from
  the actual un-terminated arguments plus the fixture's line reader, not from
  old implementation code. No extra raw-input mode or option is implied.
- Ordinary called/returned events use `tool.job`, as the chapter already says.
  A `job_killed` event instead carries a top-level **`job`** object, with
  **`reason` inside that object**, alongside `handle` and `status`. For example,
  an illustrative payload is `"job":{"handle":1,"status":"killed",
  "reason":"kill_job","output":{"kind":3,"locator":"cr/io/1"},"bytes":0}`.
  The ordinary event envelope still supplies sequence/type/time. A shutdown
  kill uses `reason:"shutdown"`; neither claims successful completion.
- The effective command directory is recorded as `tool.job.cwd`. The harness
  supplies `cwd` as a string on `run_command`, including relative directories;
  later calls omit it to test that the override did not stick. There is **no new
  launch-workspace environment variable or CLI flag supplied by this harness**.
  It launches the process in its scratch workspace and reuses Chapter 3's
  environment, including `CH02_LOG`. The chapter's library/workspace design
  remains the student's decision under the carryover rules.
