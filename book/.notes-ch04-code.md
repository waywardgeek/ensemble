## Design as ruled by Bill (2026-09-13), supersedes outline §4.6/§4.7

- NO blocking contracts (DeadlineArg/MaxBlockingTime), NO job budgets, NO
  budget policy. Jobs never auto-die; `kill_job` is the only terminator.
- Every tool call is a job EXCEPT the job verbs and `tool_limits`.
  Job: handle N (sequential, per process), file `cr/io/N`, status
  `running|done|killed`, full result text in the file, capped copy in context.
- A job call returns at: done | `ai_callback_delay` elapsed (default 3s) |
  `ai_callback_pattern` seen in output since the call began. Default 3s is fine
  because nothing dies: the model just gets to look and decide.
- Limits = {ai_callback_delay 3s, ai_callback_pattern none, max_output_bytes
  16 KiB}. Sources, later wins: defaults < pending `tool_limits` (one-shot,
  consumed by the next call) < explicit args on the call.
- `run_command`, `wait_for_job`, `send_input` take the three limit args
  directly (the model changes how long it waits on every monitoring call, so
  a separate tool_limits round trip each time is wasteful).
- `tool_limits` exists for tools whose schema we do not own (MCP, ch6): sets
  the three for the next call only. Not a job.
- `wait_for_job(handle,…)`, `send_input(handle,input,append_newline,…)`,
  `kill_job(handle)`: not jobs. wait/send return output the model has NOT yet
  seen (per-job cursor), so bytes are never repeated; the file always has all.
- `Shutdown()` at process exit: kill_job on every running job, logged as
  `job_killed{reason:"shutdown"}`. Kill = SIGKILL the process group; a stuck
  goroutine stays stuck and the result says so.
- `list_jobs`: skipped (Bill unsure; zero measured use).

### Log contract (students must not guess)
`tool.job = {handle, status, output:{kind:"handle",locator:"cr/io/N"}, bytes,
exit_code?}` on `tool_called` and `tool_returned`; absent on non-job calls.
New event `job_killed` `{job:{handle,...}, reason:"kill_job"|"shutdown"}`.

### Result text
- finished within delay and ≤ cap: the output verbatim (byte-identical to ch3
  behaviour, so ch3parity holds).
- still running: header `job N still running after Xs; output so far (M bytes):`
  + capped unseen output + hint line naming wait_for_job/send_input/kill_job.
- over cap: head + `[... K bytes omitted; full output (T bytes) at cr/io/N ...]`
  + tail; head and tail each ≤ cap/2.
- run_command file = combined stdout+stderr stream, then `exit_code: N` as the
  last line (cannot be first when streaming). ch3's exitCodeRe still matches.
