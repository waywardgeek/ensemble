# Chapter 19 outline: The crossover

Through-line stake: a reader must decide whether to trust the agent they built
with the next real piece of work, after watching it edit, test, explain and resume
that work through the interfaces they intend to use.

Scope proposal, October 8, 2026. The coordinator accepts a bounded real-work
capstone rather than an artificial new runtime feature. This outline and its
[research evidence](chapter-19-evidence.md) await independent scope review.
They do not release implementation, authorize provider calls or report a successful
crossover. Chapter 19 retains its working mapping from first-edition Chapter 20.

## What the reader actually builds

Produce one useful, independently reviewed change with Ensemble, in an isolated
checkout of its accepted second-edition source, plus a reproducible record of
how the work was obtained. The change addresses a real bounded issue chosen
before the run. The output is a patch, distinguishing checks, actual user-session
receipts and an adoption decision with explicit limits. A new service, policy
layer or automatic self-rewrite loop is not required to make this a chapter.

The operator uses Ensemble's human CLI and real optional browser. Ensemble uses
its ordinary tools to inspect and change the checkout and run the relevant checks.
Its existing GUI-MCP integration observes the actual selected view. An external
consumer exercises the same public library with independent Agents. A later
restart continues from the recorded work without repeating completed effects.
The coordinator can independently verify the patch and run checks, but those
outside actions must never be presented as work Ensemble performed.

Keep the task independent of the eventual edition-comparison experiment. This
chapter asks whether this built agent can complete and sustain a particular
real workflow. The final chapter compares editions and teaching under matched
conditions. One successful patch cannot establish a productivity multiplier,
universal superiority, unattended autonomy or better model weights.

## Proposed teaching order

1. Return to the two-agent decision. Define success as useful reviewed work with
   a trustworthy record, not a green launch or a score from an earlier chapter.
2. Choose and freeze the job: existing issue, expected behavior, file scope,
   known-good starting source, useful counterexample and stop conditions.
3. Start from an ordinary human prompt. Inspect the actual request/model/funding
   facts and tool effects. Preserve a model's mistaken explanation beside the
   artifact that corrects it.
4. Ask the agent to inspect its own selected GUI view and verify one supported
   UI action. Observe through MCP and independently in the real browser.
5. Stop at a settled boundary, checkpoint, close normally, restart and ask for
   the next step without retelling the task. Verify identity, prior effects,
   applied settings and silent historical speech.
6. Review the patch outside the agent's own account. Distinguish product defect,
   provider behavior, task failure, evidence-tool failure and missing teaching.
7. Make the adoption decision. Explain what the next real task can safely rely
   on, what still needs supervision and which limitation blocks adoption.

## Exact workflow to develop into the contract

The coordinator selects one real issue in the permitted second-edition source
before seeing the model's answer. Freeze a short task brief with affected paths,
observable expected behavior, existing failing or missing distinguishing check,
out-of-scope work and the accepted baseline identity. If no suitable issue is
available, select a bounded useful improvement and its acceptance condition;
do not plant a defect and later call its discovery a production finding.

Create a separate clean checkout and scratch data directories. Record its initial
tree and file hashes. Retain the original workspace, historical editions and
uncommitted human work; never use reset/clean as a substitute for identifying the
candidate's changes. Only the selected checkout is the agent's edit target. It
does not receive grader internals, other-client token stores or hidden answer code.
Keep the current running executable bound to its original source; editing its
source does not hot-replace that executable.

The first prompt gives the task brief and the exact mandatory skill path. Have
Ensemble read that whole skill and relevant new teaching before code edits, with
the actually delivered text/ranges recorded. A truncated read is incomplete.
Ask it to inspect the failure, make the bounded change, run the named meaningful
checks and explain what changed. Read each reply and tool result before a
follow-up. Corrections are allowed inside the stated budget and remain visible.
Do not send the expected patch or use an outside coding assistant to rescue the
initial answer while presenting it as Ensemble's work.

After the initial artifact and run freeze, the independent reviewer examines the
actual diff, output and new checks. Required repairs belong to their responsible
earlier contract/source; this chapter records the discovery rather than opening
a repair chapter. Review may request a bounded revision, but a new runtime build
gets a new source/binary identity and affected local/live gates. Keep the initial
failed attempt. Do not overwrite it with the polished answer.

## Provisional finite demonstration allocation

Propose a maximum of **40 actual model starts**: 24 on one preselected principal
route and four on each of the remaining four routes. The five routes are the
three inherited API-key adapters and the two explicit Responses funding modes.
This is a scope-review proposal, not launch authorization or an assumption that
the selected account has plan access. Use existing authorized access and current
discovery; unavailable routes stay incomplete without credential/funding fallback.

| Allocation | Concrete action and retained observation |
|---|---|
| Principal human CLI: 8 | Inspect the real issue, edit only allowed files and run distinguishing checks through ordinary tools. Record prompts, calls/results, stdout/exit status, actual file changes and any correction. |
| Principal resumed CLI: 4 | Checkpoint/close at a settled boundary, restart the same compatible store, ask about the recorded rationale and perform one permitted next step. Verify no old effect was repeated. |
| Principal GUI: 8 | Use the actual mounted Page and GUI-MCP tools to inspect the selected view, perform one supported bounded UI action and inspect applied state; reconnect and verify the same accepted work without duplicate cards or historical autoplay. |
| Principal public embedding: 4 | Two Agents receive at most two starts each. Perform independent bounded read/check tasks, close one and retain the other's usable completion/state. Record real public ownership and accounting. |
| Each other route: 4 | Fresh compatible scratch session: up to two starts for a small prescribed read/edit/check task, then a settled restart and up to two starts for evidence-based follow-up. These parity tasks are controls, not four repeated discoveries of the principal issue. |

The exact user prompts, local fixtures and acceptable effect set must be published
after scope review and before any implementation/launch. Four starts cannot
guarantee a model will finish; an incomplete result remains incomplete. Every
foreground continuation, failure, canceled admission and unexpected helper counts
at durable admission. Keep automatic maintenance off for this bounded experiment;
its accepted predecessor evidence remains separately bound. No extra model acts
as an invisible listener, judge or reviewer during the live allocation.

Proposed limits: 120 seconds per model operation; 20 minutes for each eight-start
task; 10 minutes for each four-start task. API-key runs capture a positive output
cap of 4,096; the explicitly selected plan route remains uncapped remotely under
Chapter 17. Deadlines/start counts are not remote token or charge ceilings. Report
usage by actual producing route/model/purpose, with subscription figures not
silently priced as an API invoice. No cache-read target or historical floor is
a pass condition. Any required access/discovery calls need their own finite
preflight allocation; do not hide them in a model-start count.

Stop the affected task on exhausted allowance/deadline, unresolved architectural
ambiguity, scope escape, corruption, credential exposure or inability to preserve
receipts. Use existing interrupt/close semantics and retain completed effects;
do not imply rollback. An unexpected tool call consumes its normal budget and
authority checks. Restart cannot reset the allowance. Independent work can
continue, but a failed required row prevents a successful crossover claim.

## Finite acceptance and the decision at the end

| Property | Required independent evidence |
|---|---|
| Useful work | Initial issue/brief predates answer; original and final diff; checks fail on the actual original defect or deliberately removed candidate behavior and pass on the accepted change. A self-reported PASS alone fails. |
| Real user path | Actual PTY and browser inputs; Ensemble-owned tool execution produces matching files/test output. Outside verification is explicitly separate. |
| Actual GUI integration | Real scoped WebSocket MCP calls, applied control state, before/after view and independent screenshot/text. Missing channel cannot be replaced with a fake success. |
| Resume and ownership | Stable session plus new mount/workers; no repeated old side effect, cards or speech; pending work settled before save. Public Agents have independent state and reliable completion. |
| Effective identity/cost | Actual request and response provenance, captured funding/cap, usage receipts and honest unknown-price/cache results. A picker label alone proves nothing. |
| Honest record | Immutable source/binary/launch bindings checked before replay; raw versus derived files distinguished; count all attempts; failed controls cannot pass due to an earlier path error. |
| Architecture and regressions | Existing owner/import and delivered-module checks; predecessor acceptance and relevant inherited coverage retained; deliberate integration defects caught by the intended check. |
| Review and adoption | Independent patch/teaching review, student experience before comparative feedback, retained corrections and explicit remaining limits. Bill's personal adoption is never inferred from coder use. |
