### Implementation and scope

`main/internal/skills` owns discovery, the chapter's flat frontmatter parser,
recursive dependency resolution, loaded/pending state, tool provenance and variable
renderers. `common` supplies only vocabulary/interfaces. Composition attaches the
registry to its actual Agent parent before initial rendering. Optional public
`AgentSpec` separates identity from provider configuration; both CLI and GUI
translate environment settings at their application boundary. `RegisterVar`
affects future loads. The parser accepts space-separated and multiline lists and
preserves horizontal rules after the frontmatter. It is not a general YAML parser.

Initial primary/dependency bodies render once. A load validates the whole dependency
graph before enabling anything, then returns rendered instructions through the
existing tool result. Enabled declarations and dispatch use the same registry
predicate, so guessed names cannot execute hidden handlers. Shared tools retain
initial provenance rather than being reclassified on a later dependency load;
dynamic metadata names the actual `tool_called` event. `History.LastSeq` avoids
copying the full history to capture that identity.

`unload_skill` uses the same `name` argument as `load_skill` and marks a loaded
skill pending; instructions and handlers remain available. No compaction or
removal hook was brought forward. Marking an unloaded name returns an error.
Lifecycle tools are always enabled when a primary is configured. Without a skill
specification, earlier unrestricted public tool registration remains unchanged.
The public chapter's single-shot `prompt TEXT` CLI is now present alongside chat;
all paths use the same Agent. No cache policy, memory, sub-agents or extra tool
behavior was introduced.
