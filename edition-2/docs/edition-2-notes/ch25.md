## Lessons to carry forward when relevant

- **Exercise the shipped composition root and human input path.** §25.5's
  library tests supplied the factory and user sink that the command omitted;
  they also missed failure to propagate construction capability to children
  and stdin blocked on the same turn it needed to steer. Check the actual
  executable, its real input delivery during work, and the required hierarchy
  depth when that capability arrives. A passing hand-assembled library fixture
  does not prove product wiring. This strengthens existing verification without
  requiring sub-agents or a paid fleet demonstration in earlier exercises.
- **Isolation and identity belong to their runtime owners.** §§25.1/25.6 give
  each child its own actor, tools, data directory and save, retain that data
  after shutdown, and cascade parent shutdown. Their counter example puts
  per-fleet message identity on fleet state, not a package global. Apply the
  current ownership rule now; child persistence and recursive lifetime remain
  future Chapter 25 capabilities.
- **A message is not completion.** §§25.2–25.3 separate asking for help from
  `submit`; fan-in must yield to a child's question to avoid mutual waiting.
  Replies retain sender identity. The user is an addressable recipient, never
  a spawnable/shutdown-able fleet member. These are future messaging semantics,
  not a revival of the withdrawn Chapter 6 grouped-wake exercise.
- **Steering preserves running work.** §25.4 reuses the background-job result
  path when a message wakes a tool wait; it neither kills the job nor loses its
  later result. Idle-without-submission correction is reactive and bounded,
  with three framework wakes then escalation, reset on submission, and failed
  turns reported rather than automatically retried. Add this mechanism only
  when its chapter is authorized; retain the existing interrupt/job distinction.
- **Invocation is evidence.** §25.6 reports a relative-path/working-directory
  difference masquerading as a source regression during a bisect. Compare the
  real launch, resolved artifact paths and executable identity before blaming
  code. §25.8's broad isolation mutant illustrates coupled failure: six failed
  checks are not six isolated proofs, and one broad mutant cannot establish
  that no narrower mutation is possible.
