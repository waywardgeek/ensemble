# Chapter 21: Managing the Swarm

A parent waiting for twelve children and a child executing a command can both report “running.” That label is enough to keep either from being mistaken for finished work. It is not enough to decide where an operator should look. Chapter 20 made delegation reachable from the executable; the browser still showed one conversation. Supervising the fleet meant asking its parent for reports and reconstructing the tree from tool results.

The management console makes that tree visible and opens the actual conversations behind it. Its harder job is keeping three facts separate: activity describes what an Agent is doing now, lifecycle describes the state of its work, and persistent identity determines what the application restores. An idle Agent may have submitted successfully, stopped without submitting, or finished an ordinary human conversation. A saved named peer may return after restart without any of its former task children. The screen has to tell those stories without inventing a simpler one.

## Activity is an observation, not a verdict

The four activity phases are idle, thinking, tool call and waiting. Thinking begins with a model request. Tool dispatch reports the tool name and a short argument detail. A blocking fleet operation reports waiting, and the end of a turn reports idle. These facts come from the actor and dispatch path through the existing Observer, not from browser guesses about printed text.

Activity accompanies lifecycle rather than replacing it. A submitted Agent can be idle while retaining its submitted state. A waiting parent can have descendants changing files or running commands. Its phase is neither a security assessment nor evidence that earlier effects have stopped. The phase helps locate a question; the conversation and tool results help answer it.

The short detail makes a status useful without turning it into another log. The accepted implementation keeps the tool name separately and limits argument detail to fifty Unicode characters. A file name often distinguishes the call well enough; the full arguments remain in the conversation. Detailed status also includes measured token usage. Heavy input consumption with little useful output warrants inspection, but the counts alone cannot establish that an Agent is looping.

## Persistent peers and task children

Ensemble owns the main Agent and a persistent registry of named peers. Each Agent's fleet manager owns its spawned children. Those are different relationships: named peers such as a researcher or reviewer survive application restart; task children are ephemeral and are not automatically recreated. Both can appear in the same browser tree without acquiring the same lifetime.

The registry, `ensemble.json`, records each peer's name, model, defining skill and creation time. It identifies the Agent; the Agent's own save holds its conversation. In the supplied command, named peers keep their saves and event logs under `agents/NAME/`, while the root uses `cr/` for Agent data and a separate default or explicitly selected save path. Task files still occupy the application's workspace. Separate histories do not provide private copies of the repository.

Creation builds and saves the peer, then persists its registry identity before announcing success. Empty model and skill selections inherit application defaults. Deletion refuses unfinished children and closes child admission before shutting down the peer and removing its identity and data. Without closing admission, a child could appear between the check and deletion. Application closure instead saves and stops peers while retaining their registry entries for the next launch.

Named peers have no Agent parent, just as the main Agent has none. Both normally finish in chat. Delegated children owe a submission, must resolve their descendants first, and receive Chapter 20's bounded correction when a successful turn stops without submitting. Displaying everyone beneath an Ensemble node does not make everyone a delegated worker.

The public startup path extends the owner already established in Chapter 20. CLI and optional GUI call `ensemble.New` and then `root.Start`, which installs recursive construction and the human route before restoring Agents. Existing non-fleet callers can retain `NewAgent`. Flags, authentication, terminal input and browser serving remain application concerns; conversations, tool visibility and jobs remain Agent concerns. One startup path reduces missing connections, but only exercising the executable can reveal whether it actually calls that path. A registry row proves that an identity was saved; the restored conversation proves more of what the operator meant by saving an Agent.

## Settings have two application times

A persistent application also needs to distinguish the configuration it is using from the configuration it will use next time. The GUI command's versioned `ApplicationConfig` holds provider, model, billing, reasoning and endpoint settings alongside external credential references, paths, runtime options and GUI preferences. It does not replace the public Agent constructors or impose a new loader on every CLI consumer.

Explicit `--config` mode is selected before environment builders run. Otherwise an inherited provider, skill or authentication variable could contaminate the file's meaning, or even prevent startup despite the file being valid. Relative paths resolve against the file's directory, not the launch directory. File mode accepts only the explicit port, GUI-directory and GUI-debug launch overrides, reports them, and rejects competing provider or Agent flags. Without a configuration file, legacy environment and flag behavior remains available.

Loading requires a supported explicit schema version and rejects unknown fields, invalid values, malformed or trailing JSON and embedded credential contents. Secrets stay in the referenced external key file or authentication store. They do not belong in browser settings payloads, flag defaults or help and error output. Saving validates first, uses private directories and a private same-directory temporary file, and replaces the file atomically. The saved in-memory snapshot is published only after success; a failed write or rename must leave the prior file and snapshot usable.

The settings view shows the file path and separates active provider values from saved next-launch values. Provider, model, billing and reasoning changes require an explicit Save and restart. They do not rebuild a live Engine, and newly spawned children continue inheriting their parent's resolved running configuration. Otherwise a saved edit could quietly give a child different credentials or billing while its parent retained the old configuration. Manual file edits also wait for restart; there is no implied live watcher.

Speech, theme, font and budget preferences remain immediate. In file mode, root preferences share the application file without overwriting provider fields. The old root `cr/settings.json` is ignored, not deleted; children retain local preferences. This mixture makes Save correlation consequential. Another tab's acknowledgment or an unrelated preference broadcast cannot mark a provider edit saved. Edits made during an outstanding save must survive its reply, and normalized credential paths must be handled without revealing their contents.

These are startup and interaction properties, not merely parsing properties. Supplying a constructor with correct values cannot establish isolation from a poisoned environment, correct path resolution from another directory, or the browser's distinction between pending and saved edits. Likewise, a successful Save acknowledgment cannot establish that the running provider changed; in this design it should not have changed.

## Supervision stays inside the owner's fleet

A model-callable management operation resolves its target through the calling Agent's fleet manager, which contains its direct children. Foreign and nonexistent targets both return “unknown agent.” The caller does not receive a global map and then filter it. The trusted browser can walk the Ensemble to select conversations, but that broader visibility is not a fallback authority for model tools.

The same rule governs durable results. A submission file is readable through this interface only after resolving an owned child. Keeping a file after shutdown does not turn `get_submission` into a global archive lookup. This containment protects management operations; it is not process isolation or protection against every route through shared files and permitted tools. A rejection is meaningful alongside a successful operation on an owned child. A manager that refuses everything is contained but useless.

`wait_for_agent_change` observes a selected set of children for state changes, exits, parent messages, matching output or lack of progress. The accepted implementation snapshots those children, waits on the existing change notification or a short timer, then compares their state. The timer notices a busy child that stops progressing even when no notification arrives. This avoids adding a durable event-distribution system for a waiter that needs current state. Its work grows with the selected set; small fleet exercises establish no thousand-Agent performance claim.

An early version confused a notification with evidence about a particular child. A question from an unselected child advanced a manager-wide message counter, and the wait reported its selected child as the sender. Both requests were otherwise parked. Tracking message progress per sender fixed the attribution: the selected child's question still woke the wait, while the other child's question no longer impersonated its progress.

The wait has three distinct clocks. `timeout_seconds` bounds the observation job; `stuck_seconds` measures a busy child's lack of progress. The ordinary tool callback delay merely returns control with a running handle. It does not cancel the observation. A notification tells the waiter to inspect state, not what it is entitled to report.

Messaging separates steering from asking another question. `send_message` gives a busy child a hint between tool calls or starts a new turn when it is idle. Its recent output and cursor let the caller continue reading without replaying everything. `wait_for_agent` returns new finalized assistant text and tool output beyond that child's cursor, or returns when the child is idle. Streaming fragments belong to the GUI path: returning a fragment here and its completed replacement later would count the same output twice. `ask_agent` instead queues a distinct question and waits for that turn's result. Seeing new output is not equivalent to receiving the answer to that question.

Stopping also has more than one meaning. Graceful `shutdown_agent` waits for current and queued turns. `kill_agent` cancels the child's lifetime, including in-flight work, jobs and descendants, then removes it from the fleet. Application teardown needs the cancelling path so an unresponsive child cannot keep the process open. `interrupt_agent` preserves the Agent and independent jobs while ending its current turn: `now` cancels immediately, and `after_tool` stops at the next tool-report boundary. An acknowledgment proves delivery; observing the boundary and a later answer from the same Agent establishes the more useful behavior.

## A durable result is not current completion

Chapter 20's default text submission and custom JSON contract remain intact across supervision. `Fleet.SubmissionData(id)` returns a typed `Submission`, with default text in `Result` and custom JSON in `Payload`. The older string-only `Submission(id)` refuses custom data rather than silently forcing every caller to parse it. The tool returns `agent_id` with either `result` or a nested `payload`; status and joins preserve that object too. Where `ask_agent` must return text for a custom-only answer, it returns compact JSON rather than a blank successful string. Returned raw JSON belongs to the caller, not to mutable internal storage.

Accepted submissions append to the child's `submit.md`. Legacy rows contain the text result; versioned custom rows retain both schema and payload, so an older result keeps the contract that accepted it even when a later task uses another. Stored custom data is validated under that contract. Malformed rows and unknown versions are errors, not reasons to quietly return an older success. JSON string encoding keeps newlines inside a result distinct from the row boundaries.

Retrieval tries memory before durable storage, but it still starts with owned-child lookup. An explicitly respawned child can therefore expose a previous durable result while its new task remains running and unsubmitted. Restarting the application does not recreate that child automatically. The result may also survive as a retrieved tool result in its restored owner's history, which requires no live child at all to display.

Submission and disposal have their own ordering. Acceptance can wake a join before the submit tool has appended its result and the actor has finished completion and saving. Disposal must wait for reliable completion and drain, not merely the submitted flag. Invalid data remains unsubmitted; a durable old result cannot satisfy the new task's obligation. These rules keep result availability, task completion and safe teardown from collapsing into one misleading bit.

## Selecting a conversation without disturbing it

The browser tree follows actual ownership. A synthetic Ensemble node contains the main Agent and named peers; each Agent contributes its children recursively. A local name alone cannot identify a node: `reviewer/helper` and `coder/helper` are distinct. The accepted tree carries an ownership-path key alongside the local ID, parent, persistence, lifecycle and activity. Initial complete-tree delivery and subsequent updates let a newly connected browser see current state without reconstructing all earlier transitions.

Selection belongs to a browser connection. Each Agent has its own retained conversation view, partials and replay cursors. Selecting it resets that connection's Artifact scroll, replays retained history and then continues live output. Another tab can keep reading another Agent while both receive tree changes. A global partial map would let response-local IDs from different conversations collide.

Changing the view also crosses a control boundary. Before selection, the browser cancels outgoing speech, clears its speech and typing pause causes, and sends `unpause` before `select_agent`. Otherwise leaving a conversation could strand its pending tool behind a pause gate. Late speech callbacks and queued output from the outgoing view must not alter the incoming Agent's pause. Correct isolation means the outgoing tool proceeds without another prompt while an incoming Agent that was already paused stays paused.

Structured submissions use the ordinary conversation surface, with tool arguments and results rendered safely as text while nested data remains intact underneath. Reselection and reconnect within the same application can replay the registered child's result. After restart, the restored owner's history can show its retrieved result without resurrecting the ephemeral child. Finding a marker in a frame cannot establish this preservation; arrays, booleans and nulls must survive in the actual object.

Fleet observation must not make browser speed part of the actor's lifetime. Tree traversal can take several managers' locks, so a small coalescing worker performs it outside the synchronous Observer. Notifications request a refresh instead of making the actor wait while the GUI walks the hierarchy.

Selection exposed a more direct failure. Repeated clicks from a browser that stopped reading filled the replay queue. The receiver waited to enqueue history while holding the server mutex. Disconnect then needed that same mutex to finish shutdown. A slow tab had stopped the server.

The correction admits a whole replay as one queue batch and publishes the selected view only after admission succeeds. A connection unable to accept the batch is disconnected and can reconnect for a fresh replay. A larger buffer would merely postpone the blocked send; dropping the tail would silently lose conversation. Other connections and Agents must remain independent of that slow reader.

Visible creation and deletion complete the tree's controls. Creation supplies a name, model and defining skill to the existing Ensemble owner. Deletion displays the rejection when unfinished children remain. The GUI does not bypass the lifetime rule simply because a human clicked the button.

## The task succeeded; the history was wrong

[The source records a browser run](../edition-3/chapter-21.md) in which a named peer, `console`, created one `helper`. The child implemented a small slug function, wrote three unit tests, ran them successfully and submitted. Its parent monitored activity, joined, retrieved the submission, independently reran the tests and wrote the outcome. The capture showed all four activity phases and selection between both conversations. An unused named peer was created and deleted. Normal shutdown and restart restored `console` and its conversation without another inference request; `helper` did not return.

That paid run used the earlier peer-submit policy. Its named peer submitted, whereas the current policy lets named peers and the main Agent finish in chat. The historical capture demonstrates neither that changed policy nor a fresh run of today's executable.

It did reveal something the passing tests missed. The screenshot showed idle activity beside `input_pending`, including after restart. Runtime work had ended, but retained history still claimed that tool results awaited another request. Ordinarily the next request consumes that pending input. Successful fleet submission ends directly, leaving no next request to conceal the stale state.

The correction records the existing `turn_ended` fact after the submitted tool batch drains and before completion and save. Replay can then present the truth already owned by history. Forcing every selected Agent to look idle would repair the screenshot by hiding genuine work. A separately parked request supplied the necessary contrast: completed and restarted conversations should be idle, while an outstanding request remains `in_flight`.

The source's corrected behavior was checked through the real runtime, WebSocket selection and restart with a local provider peer. The earlier paid capture retains its bad label. There was no claimed paid rerun or migration of old incorrect saves. Successful task work, discovery of the display defect and the local correction check are separate pieces of evidence.

The original grader had an even earlier observation failure: CLI scenarios omitted the model, and its browser probe launched the headless command with GUI flags. Those launch failures established neither broken fleet behaviors nor working ones. The revised driver crossed the actual application boundaries, while focused controls addressed selected-child attribution, finalized cursors, interruption and slow clients. None makes a small coding task exhaustive evidence for the console. The useful distinction is concrete: supervision must preserve the state and ownership that make a report true, even when the work itself has already succeeded.
