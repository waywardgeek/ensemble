# Chapter 20: The Ensemble

The first-edition executable reached its first spawn request and answered “no agent factory configured.” The fleet tests had supplied factories of their own; application startup had supplied none. The library could manage a child that the product could not create. This was not a missing convenience around an otherwise finished feature. Until the executable connected construction to the tool that requested it, spawning did not work for its user.

The GUI encountered the same boundary from the other side. After the first edition's architecture repair, Bill wanted the Artifact scroll for Homebrew-VTT. The component was reusable, but its Go package remained behind `internal/`, where an outside application could not import it. The repair had missed a boundary nobody had tried to cross. A terminal fleet and a separately shipped GUI look like different projects, but both depend on someone outside the component being able to reach a complete, supported capability.

Chapter 19 established confinement for model-requested operations, with policy in the existing Config and child permissions allowed only to narrow. Here that ownership extends to a terminal parent constructing children, alongside an outside application using the public GUI. The browser still presents one Agent. A fleet panel comes later; neither child construction nor its completion rules should depend on that panel existing.

## A public boundary needs an outside caller

In the chapter's design, the root module owns Agents, Config, providers, conversations, tools, the stream actor, persistence and fleet management. The public `ensemble/gui` module owns browser-facing connections: the WebSocket bridge, settings handler, MCP relay and static assets. Its constructor, `gui.New(root, agent, log)`, accepts public values and returns a server with handlers and an explicit lifetime. An optional executable assembles them. Importing the core must not import the browser transport.

Public spelling alone is insufficient. A constructor is unusable to an outside application if its arguments have internal types, or if initialization still requires a private helper. The source's outside consumer constructs real public inputs, records a public event for replay, sends a prompt and reaches the relay. Those are distinct uses of the boundary. Successful construction cannot establish that replay works, and a rendered replay cannot establish that a new prompt reaches a provider.

The dependency graph needs the same skepticism. The first-edition GUI move left an indirect path from headless core tools through the MCP package to Gorilla WebSocket. Browser code had moved, but a WebSocket client remained in the headless protocol module. Separating that client removed the browser implementation from the core import closure. Checking a headless consumer alongside a GUI consumer matters: the latter is the positive control showing that the dependency check can actually find the transport. A clean import closure establishes dependency reachability, not runtime behavior.

The GUI constructor also needs a complete owner relationship. The first-edition Hub took a bundle of controls and acquired a current-model closure afterward. Reading the model live was necessary because an operator could switch it, but another caller could forget the late assignment. Moving the closure into a keyed callback struct did not make it mandatory: omitted Go fields still receive zero values. The accepted constructor instead checks the supplied root, Agent and logger, including that the Agent belongs to that root. Through the Agent it reaches configuration, Engine, history and pause state; Ensemble supplies observations. The server owns browser connections and frontend settings, not the Agent it displays. The application controls both lifetimes.

The public MCP relay accepts a listener chosen by the embedding application and forwards JSONL requests through a connected browser. Two callers may use the same JSON-RPC ID while replies arrive in reverse order; each must still receive its own response with its original ID. With no browser, the error is immediate and correlated. A connected but silent browser instead leaves work pending until a relevant connection or the server closes. Continuing to read the caller's socket detects disconnects and releases that caller's wait. Server closure closes listeners and joins connection workers. A no-browser error cannot establish these pending-work lifetimes.

## Deployment includes assets and their owner

The chapter's deployment model embeds the shell, styles and JavaScript modules in the GUI package. A built executable can therefore run away from the checkout, while an explicit `--gui-dir` selection lets a developer serve disk assets. The choice remains explicit: silently discovering a nearby source directory would make the same binary behave differently depending on where it starts.

Serving a path is not the same as serving the right asset. In the source's student run, an initial check accepted HTTP 200 from a directory listing that contained no GUI. Requiring the actual application shell exposed the defect. The response body was the missing evidence. Likewise, a settings acknowledgment shows that the control was received; the next provider request's model field shows whether a turn-boundary model switch took effect. Neither replies counted nor successful HTTP status codes substitute for observing the behavior being claimed.

`gui.Assets()` exposes a read-only filesystem because some callers need less than a server. The embed anchor stays private: Go requires that anchor at package scope, but exporting the variable would let callers replace its binding even though the embedded files are read-only. Returning `fs.FS` exposes the resource without that mutable public binding. A host can serve the Artifact scroll and renderer modules, mount the component in its own page and omit Ensemble's application shell. The shell owns its WebSocket connection, sends incoming events to the scroll and sends outgoing controls. The scroll and renderers own presentation. The extractions were substantially in place already; deployment should preserve that separation rather than invent a second UI protocol. A component-only page rendering a message while the application index is absent establishes a different kind of reuse from a full GUI session.

An embedding application owns more than HTTP registration. It supplies provider configuration, authentication, storage, logging, listeners and orderly shutdown. The source's small external application starts a fresh conversation; it is not evidence of resuming a persistent task. It prints newly allocated loopback addresses to avoid accidentally observing another running instance. Such details make the observed boundary attributable to the application under examination.

That application must also distinguish the provider configuration resolved by a running Agent from settings saved for the next launch. Children inherit their parent's resolved, running configuration; they do not re-read environment variables or saved next-launch settings. Permitted model and local-preference overrides remain explicit. When Chapter 21 introduces saved provider edits, those edits must not silently switch a new child's billing or credentials while its parent retains the old values. Credentials remain application and Agent configuration, not routing fields in a model-visible specification.

The source records a second-edition deployment from a fresh directory: Chrome loaded the embedded shell and six supporting assets, and a provider-backed task wrote and read back a 42-byte file before normal exit. That is local evidence for the embedded application and that task. It does not establish component-only rendering or relay teardown, which have separate boundaries. Nor is the record a fresh observation of today's executable.

## Children have separate state, not separate worlds

A terminal fleet begins with real construction. Each child is a full Agent with its own actor, tool visibility, conversation, save file and data directory. Sharing a parent's conversation and wrapping several calls in child names would not provide those properties. A failed child can be shut down and respawned without replacing its parent's conversation. The Agents share a process, however; separate state is not process-crash isolation.

Each Agent's manager tracks children, while an application-supplied `AgentFactory` constructs them. The factory receives the actual parent and child specification and returns an Agent. The manager loads its save, registers it and starts the task. In the restarted Edition 3 design, the existing public Config supplies the configuration role; a second configuration system is unnecessary. Application composition stays in the factory, while registration, parentage and lifecycle stay in the library.

The terminal installs the factory on Ensemble before constructing its Agents. The manager derives child IDs and paths from the parent; `NewChildAgent` checks the actual owner relationship and clamps the specification. Descendants reach the shared root through their real parent relationships, rather than relying on copied factory callbacks. A separate human sink makes the root's upward questions deliverable. An embedder that installs no factory retains its ordinary tool surface.

State lives under distinct child data directories, such as `cr/children/<id>/`. Each save contains that child's conversation, event log and tool state. Shutdown preserves the directory, and restarting the same child ID loads its saved conversation before starting the new task. That does not require a private task workspace. Several children may work on the same repository while their conversation and runtime files remain separate. File ownership and shared-edit coordination still need to be assigned. Independent Agent state is not filesystem isolation, and neither establishes freedom from conflicting changes.

Chapter 19's narrow-only rules apply at construction: a sandboxed parent cannot create an unsandboxed child, and a parent without web access cannot grant it. Runtime role instructions must agree with that construction. A worker's instructions should be composed from the authored base, not from an already-rendered root prompt that prohibits submission. A worker choosing another model also needs that model's policy without duplicated or stale policy text. Successful construction alone cannot reveal an instruction that tells the child not to perform its required completion action.

## A parent must remain able to answer

The fleet is a tree, not a flat collection of workers attached to the root. A child's routing ID accompanies, rather than replaces, its actual Agent parent relationship. A grandchild's question therefore goes to the child that delegated its work; it reaches the human only through the necessary parent steps. Hardwiring every parent to the root would make a shallow demonstration look correct while breaking recursive responsibility.

The human has a configurable address but is never a managed child. Uniform addressing does not grant authority to spawn, shut down or inspect the status of a person. Keeping the human out of the children map avoids making every lifecycle operation compensate for that false equivalence.

Questions suspend their askers. `send_message_to_parent` creates a pending question and waits for a reply. When the parent is the human, the root sink displays the question and retains its reply channel until terminal input arrives. Incoming messages retain sender identity. The question, pending state and reply routing must survive the interval when no model turn is actively producing text.

The first edition initially supplied the parent link only at submit time. A child could deliver its finished work, but it had to claim completion to ask for help. Bill caught that conflation: asking needs its own verb, available before finishing. A separate collision appeared in the student implementation when a parent and child with the same local name generated the same first question ID. The child question overwrote a pending question to the human. The fix allocates IDs at the recipient's manager under the lock protecting pending questions—the scope in which replies must be unambiguous.

`respond_to_parent_message` can omit the opaque message ID when exactly one matching question is pending. The source describes this as removing a reliability tax: the model need not copy an identifier out of prose when there is only one possible answer target. More than one pending question still requires an unambiguous selection. Convenience cannot replace question identity.

Fan-in must accommodate this conversation. `join_agents` waits for the selected children to submit, or all managed children when the selection is empty. If a child asks a question during the wait, join returns a tool result so the parent can answer and resume joining. Otherwise the parent would wait for a result from a child that was waiting for the parent.

Human steering needs a different interruption. Input can wake the parent's wait while the underlying join job remains alive, allowing the same handle to be collected later. The terminal therefore must read input independently of the goroutine waiting for tool completion. The first-edition command loop did not: it promised steering in a comment while blocking the very reader that could deliver it. No amount of wake logic inside the Agent could compensate for that executable wiring.

Message wake is independent of the callback timer. Existing `tool_limits` supplies a one-shot override for the next call, not a per-tool-name timeout map. An interrupt with no current waiter is a no-op; leaving it pending would let a later wait consume a stale signal. Terminal `/reply` input answers a pending human question rather than becoming a new task, and the actor remains the single place ordering conversation changes.

Status and shutdown complete this ownership story. `agents_status` exposes the managed children and their current states. `shutdown_agent` recursively closes a child and its descendants and removes it from the Manager. It is a lifecycle operation, not a way to pretend that unfinished work produced a result.

## A result contract is not a verdict

Delegated completion occurs through `submit`, not through a sentence saying the work is finished. By default its object contains a required string `result`, preserving the familiar text-child contract. A caller can instead provide a `submit_schema` through `spawn_sub_agent` for a particular child. The source's reviewer returns a summary and an array of findings, each with a path and boolean `fixed`. That gives the parent data it can consume without extracting structure from narrative prose.

This schema belongs to the spawned instance. It is validated and defensively copied before construction effects, and the factory's returned child must retain it. The same compiled contract supplies the model-visible declaration and validates actual arguments before persistence or completion notification. Ordinary grandchildren retain their default contract unless their own spawn specifies another. A parent's reviewer schema is not an inherited conversation-wide rule.

The chapter deliberately limits this validator to a declared subset of JSON Schema Draft 2020-12. The root must declare object type; nested schemas may be objects or booleans. Object and array constraints, exact numeric bounds, string bounds and patterns, enums and constants are enforced rather than merely advertised. Annotations insert no defaults and coerce no values. Unsupported keywords and all references are refused at launch; schema resolution never fetches a URL or reads a file. Numbers must survive without rounding through `float64`. The schema itself needs validation, not just a check of its keyword names.

Admission limits bound schema and payload bytes, value-node counts, depth and numeric-literal complexity. They refuse rather than truncate. The combined canonical schema-by-payload byte budget can reject a pair whose members each fit their individual limits; it is a conservative work bound, not a CPU deadline. A real validator still has to enforce the admitted semantics. The public string convenience method enters that same validator and cannot bypass a custom contract. Arrays, booleans, nulls and nested objects remain JSON data through joins, status and durable storage; a string containing JSON is not an equivalent result.

Persistence distinguishes compatibility from an explicit contract. The default text path accepts and ignores extra keys, storing the normalized result object. An explicit custom schema preserves the complete object even if its shape resembles that default. Its JSONL row in `submit.md` includes version 1, the schema and the payload. An unknown version or malformed row is an error, not permission to silently return an older valid submission.

An invalid submission leaves the child unsubmitted and does not satisfy a join. The source's controlled reviewer example omits `fixed`, receives a validation error, then supplies boolean `false`. Inspecting the accepted nested payload and saved row establishes more than finding a marker somewhere in printed output. Retaining a default text child and an ordinary grandchild also checks that the custom contract has not leaked into unrelated instances. Defensive copies protect installed schemas and submitted payloads from later caller mutation. These are ownership properties, not just parsing details.

Shape still says nothing about truth. A well-formed verdict can be unsupported, and `fixed: true` can describe a change that was never made. The parent must examine the evidence and decide whether the child's claim is useful. Schema validation makes the handoff mechanically usable; it does not transfer the parent's responsibility for accepting the work.

The same precision applies to completion. A child with unfinished descendants cannot submit until it joins or shuts them down. If a delegated child becomes idle after a successful turn without submitting, the framework supplies a corrective wake. After exactly three consecutive wakes it stops trying and reports failure to the parent, with no fabricated submission. Submission resets the count; an unresolved failed child also prevents its parent from submitting until it is shut down. The source records an important correction: initially the exhausted child remained labelled running, so the parent could keep waiting for work the framework had stopped pursuing. Failed is a necessary state, not an inconvenient presentation detail.

A failed provider turn follows a different path. An HTTP rejection or execution error is reported directly, not fed into the three-wake loop. A refusal delivered as a successful model response may still be an ordinary unsubmitted turn; classification follows the runtime outcome rather than an interpretation of the prose. Wake attempts and escalation are recorded so that the missing submission is inspectable. The bound limits correction attempts, not the time to a good answer or the model's willingness to cooperate.

This policy is explicitly narrower than “all Agents submit.” The human-facing main Agent finishes with a normal chat answer, and a named peer addressed directly by the human is not automatically a delegated worker. Presence of a factory does not confer delegated status: correction checks the actual Agent parent in the library's completion path. Explicit root submission remains available under the same admission rules, but ordinary chat completion needs no corrective wake.

Finally, accepted submission precedes quiescence. Publishing a result can wake join while the child's submit tool still needs to append its result and the actor still has completion and save work to finish. A caller disposing of that worker must wait for reliable completion and drain. Interrupting it inside the submission callback risks losing the final work that makes the accepted result durable.

## What the executable and the observations can establish

The source's five first-edition wiring failures fit together. The application omitted the factory, omitted the human sink, failed to propagate the factory to children, required unnecessary message-ID copying and blocked input on the tool-wait goroutine. Fixtures had supplied enough surrounding machinery for the library paths to work. The delivered executable had not. A three-generation exchange reveals the propagation failure that a parent-and-child example need never encounter. A question to the human exercises a sink that child-to-parent messaging alone cannot establish. Library and executable evidence answer different questions.

A historical cross-chapter sweep found a separate defect: a package-level atomic message counter generated usable IDs but put per-fleet mutable state outside the fleet. Moving it onto the messaging state, under its existing lock, restored the owner. Successful routing scenarios had not exposed that scope error. Behavioral success is not evidence that every state lifetime is sound.

The source also records failures in the apparatus used to observe behavior. A cross-chapter comparison appeared to blame an unrelated one-line change for event-log failures. Absolute worktree paths and relative live-tree paths produced different results because the harness changed its working directory and resolved the log path differently. In another probe, the final report appeared but EOF never arrived: killing a `go run` wrapper had left a child holding the output pipe. Executing the built binary directly fixed supervision. Both cases required examining how the observation was produced before assigning a product defect.

The recorded terminal fleet gives a particularly useful split between delivery and compliance. Three children implemented and tested arithmetic functions. One asked whether negative integers mattered; the parent answered yes. A malformed shell command failed, and the model corrected it. That was task-level recovery, not the framework automatically retrying a failed turn. A terminal hint then woke the parent's join wait without killing the job. A later wait on the same handle collected all three submissions, and the parent ran combined assertions; independent execution of the files also passed.

Yet the requested `STEER_COBALT` marker was absent from the parent's final result. The exact hint appeared in a later provider request. Delivery worked; compliance did not. This historical run also used the earlier root-submit policy. Its parent's submission is not a demonstration of the current rule that the main Agent answers in chat while delegated children submit. Preserving those qualifications makes the record useful: it shows which mechanisms were observed without silently promoting them into evidence for changed behavior.

The successor inherits two reachable boundaries to maintain. An outside host must be able to use the GUI without private imports or accidental transport dependencies, and the terminal must actually install the factory, routing, input and completion machinery that its fleet tools promise. Beneath both are owners with distinct lifetimes: an application closes its server, a Manager owns its children, an Agent owns its state, and a parent evaluates the work handed back. The next chapter can expose that fleet through the existing frontend without making visibility a substitute for those responsibilities.
